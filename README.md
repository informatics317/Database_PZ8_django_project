# Центр управления заявками и бронированием оборудования

Учебный веб-проект на Django. Пользователи работают с тремя частями одного сайта: учебный портал, система заявок и бронирование оборудования.
Страницы получают данные через REST API (Django REST Framework) без перезагрузки.

* Сайт: https://database-pz8-django-project.onrender.com
* Репозиторий: https://github.com/informatics317/Database_PZ8_django_project

### Назначение

Проект предназначен для студентов и сотрудников кафедры. Студенты создают заявки и брони, методисты кафедры подтверждают и завершают брони, ведут заявки, администратор управляет данными через `/admin/`, также как и методист может изменять статусы заявки и брони, менять и удалять данные.

Проект решает три задачи:

1. **Учебный портал** (приложение `accounts`): факультеты, курсы, группы, профили студентов, дашборды с диаграммами.
2. **Заявки** (приложение `tickets`): студент создаёт заявку (например, «Не работает проектор»), а методист или админ по очереди присваивают ей статусы «Новая» - «В работе» - «Выполнена».
3. **Бронирование оборудования** (приложение `bookings`): студент бронирует проектор, компьютер или микрофон, методист или админ подтверждает бронь, и свободного оборудования становится меньше.



### Функциональность

**Что можно делать на сайте:**

* входить по логину и паролю (все страницы и весь REST API доступны только после входа);
* создавать, смотреть, менять и удалять заявки и брони;
* фильтровать заявки по статусу, а брони по статусу и оборудованию;
* смотреть историю каждой брони и статистику по статусам;
* смотреть дашборды учебного портала.



**Правила и ограничения:**

* студент видит только свои заявки и брони, чужие недоступны (ответ 404);
* методист (группа «Методист») и администратор видят всё;
* подтверждать и завершать брони могут только методист и администратор (иначе 403);
* статусы меняются только по порядку, другие переходы дают ошибку 400;
* подтвердить бронь можно, только если оборудования хватает;
* удалять можно только брони в статусах «Создана» и «Отменена»;
* название заявки и цель брони должны быть не короче 5 символов;
* локальная база (SQLite) и облачная (PostgreSQL) это две разные базы, данные между ними не переносятся;
* регистрации на сайте нет, пользователей создаёт администратор в `/admin/`.

### Подготовка

Нужны **Python 3.13** и **Git**.

Проверка в PowerShell:

```
python --version
git --version
```



Скачиваем проект и создаём виртуальное окружение:

Powershell:

```
git clone https://github.com/informatics317/Database_PZ8_django_project.git django_auth
cd django_auth
python -m venv .venv
.\\.venv\\Scripts\\Activate.ps1
```



Если PowerShell пишет, что запуск скриптов запрещён, выполните
`Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` и снова активируйте окружение.
В начале строки должно появиться `(.venv)`.

Устанавливаем библиотеки:

```
pip install -r requirements.txt
```



### Настройка

Настройки хранятся в переменных окружения. Файл `.env.example` – только образец, сам проект его не читает.
Настоящие значения в Git и в отчёт не попадают.

|**Переменная**|**Зачем нужна**|**Пример для локального запуска**|
|-|-|-|
|`DJANGO_SECRET_KEY`|Секретный ключ Django, без него проект не запустится|`local-secret-key-for-learning`|
|`DJANGO_DEBUG`|Режим отладки (по умолчанию `False`)|`True`|
|`DJANGO_ALLOWED_HOSTS`|Адреса, на которых сайт работает, через запятую|`127.0.0.1,localhost`|
|`DJANGO_CSRF_TRUSTED_ORIGINS`|Адреса сайта с `https://` для защиты форм|не нужна|
|`DATABASE_URL`|Адрес базы PostgreSQL; если не задан, берётся SQLite|не задаем|

Задаём переменные в PowerShell (они действуют только в этом окне):

```
$env:DJANGO_SECRET_KEY = "local-secret-key-for-learning"
$env:DJANGO_DEBUG = "True"
$env:DJANGO_ALLOWED_HOSTS = "127.0.0.1,localhost"
```



В новом окне PowerShell их нужно задать заново. Настоящие значения секретов (особенно `DATABASE_URL`) нельзя нигде отображать.



### Запуск

Для создания миграций выполните:

```
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```



* `migrate` создаёт таблицы в базе. В терминале должны быть строки `OK`.
* `createsuperuser` создаёт администратора (спросит логин и пароль).
* `runserver` запускает сайт на http://127.0.0.1:8000/. Для остановки: `Ctrl+C`.



### Тестовые данные

Чтобы страницы работали нужны данные. Откройте http://127.0.0.1:8000/admin/, войдите администратором и добавьте:

1. Группу **«Методист»** (Authentication and Authorization - Groups).
2. Категории заявок (Tickets - Categories), например «Оборудование» и «Программное обеспечение».
3. Оборудование (Bookings - Equipments): «Проектор» (всего 3, свободно 3), «Компьютер» (10 и 10), «Микрофон» (5 и 5). В поля «всего» и «доступно» вводятся одинаковые значения.
4. Двух пользователей: студента и методиста (методиста добавьте в группу «Методист»).

### Проверка

1. **Сервер.** Откройте http://127.0.0.1:8000/healthz/, должно быть `{"status": "ok"}`.
2. **Интерфейс.** Войдите на сайт. Страница «Бронирование оборудования» оформлена в стиле Tabler и CSS (синяя панель меню, карточки), в выпадающем списке видно оборудование с остатками.
3. **API, чтение.** После входа откройте `/api/equipment/`, будет список оборудования в формате JSON.
4. **API, изменение.** На странице бронирования создайте бронь. В браузере нажмите F12 (или Fn + F12), вкладка Network, Fetch/XHR: видно запрос `POST` с кодом 201.
5. **База данных.** Остановите сервер (`Ctrl+C`), запустите снова командой python manage.py runserver и обновите страницу. Созданная бронь должна быть на месте.
6. **Бизнес-правила.** Войдите методистом и подтвердите бронь: свободного оборудования стало меньше. Если подтвердить ещё раз, будет ошибка «Недопустимый переход статуса.».
7. **Тесты.** Команда `python manage.py test bookings` покажет `Ran 2 tests` и `OK`.


### REST API

Все адреса `/api/...` работают только после входа.

|**Метод**|**Адрес**|**Что делает**|
|-|-|-|
|GET|`/healthz/`|Проверка сервера (без входа)|
|GET|`/api/categories/`|Список категорий заявок|
|GET, POST|`/api/tickets/`|Список заявок (фильтр `?status=new`), создание|
|GET, PATCH, PUT, DELETE|`/api/tickets/{id}/`|Одна заявка, смена статуса|
|GET|`/api/equipment/`|Оборудование и остатки|
|GET, POST|`/api/bookings/`|Список броней (фильтры `?status=`, `?equipment=`), создание|
|GET, PATCH, PUT, DELETE|`/api/bookings/{id}/`|Одна бронь|
|POST|`/api/bookings/{id}/confirm/`|Подтвердить (методист, администратор)|
|POST|`/api/bookings/{id}/complete/`|Завершить (методист, администратор)|
|POST|`/api/bookings/{id}/cancel/`|Отменить|
|GET|`/api/bookings/{id}/history/`|История брони|
|GET|`/api/bookings/stats/`|Число броней по статусам|

Пример: смена статуса заявки.

```
PATCH /api/tickets/5/
Тело запроса: {"status": "progress"}
Успех: 200 и JSON заявки
Ошибки: 400 (недопустимый переход статуса), 404 (заявка чужая или не найдена)
```


Полное описание с примерами ответов и ошибок: [docs/api.md](docs/api.md).



### Развертывание

Сайт публикуется на Render (бесплатная версия): отдельно база PostgreSQL и Web Service. Коротко:

1. Создать PostgreSQL на Render и запомнить **Internal Database URL** (для сайта) и **External Database URL** (для миграций с компьютера) Оба секретные, показывать их нельзя.
2. Создать Web Service из репозитория GitHub (ветка `main`).
Build Command: `bash build.sh`. Start Command: `gunicorn config.wsgi:application`.
3. В разделе Environment задать пять переменных из раздела «Настройка».
`DATABASE_URL` здесь равна Internal Database URL, а `DJANGO_DEBUG` равна `False`.
4. Один раз выполнить миграции в облачной базе с компьютера: подставить External Database URL в `DATABASE_URL` только на время команды python manage.py migrate.
5. Проверить `/healthz/` и войти на сайт.



**Важно:** миграции при сборке на Render не запускаются, их делают отдельно. Локальная SQLite и облачная PostgreSQL – это две разные базы, данные между ними сами не переносятся.



Подробная инструкция: [docs/deployment.md](docs/deployment.md).



### Типичные ошибки

|**Что видно**|**Почему так**|**Что сделать**|
|-|-|-|
|`ImproperlyConfigured: Set DJANGO_SECRET_KEY`|Не задан секретный ключ|Задать `$env:DJANGO_SECRET_KEY`|
|На Render «Bad Request (400)»|Адрес сайта не указан в `DJANGO_ALLOWED_HOSTS`|Исправить значение (без `https://`)|
|Сайт без оформления|Не собрана статика|Проверить `collectstatic` в `build.sh`, сделать Manual Deploy|
|`no such table` или `relation does not exist`|Не сделаны миграции|Выполнить python manage.py migrate|
|На Render ошибка 403 «CSRF»|Неверный `DJANGO_CSRF_TRUSTED_ORIGINS`|Указать адрес сайта с `https://`|
|Списки оборудования и категорий пустые|В новой базе нет данных|Добавить данные в `/admin/`|



Остальные случаи: [docs/troubleshooting.md](docs/troubleshooting.md).
